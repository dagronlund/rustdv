## 0. The premise
rustdv removed UVM's `build_phase` and `connect_phase` and, with them, the
entire late-binding surface: path-addressed configuration, factory
overrides, and TLM connection. Each removal was recorded locally as
"resolved by redesign"; the aggregate — that rustdv became a **closed-world**
framework, unable to configure or override anything you did not write —
was never recorded anywhere.

The book teaches rustdv as UVM-in-Rust, which creates a reader expectation
the framework does not honor. Restoring that capability is the point of
this branch.

**We are not bound by IEEE 1800.2.** Improve where Rust genuinely allows.
Do not lose capability while calling it an improvement.

### 0.1 What happened, in Ray's words (the mission)

The first pass at rustdv was built on the belief that the UVM was designed
by "primitive Python people who didn't understand the wonder of typing." On
that belief it **destroyed the dynamic component build/connect process that
is essential to the UVM, along with the TLM FIFOs that encapsulate Queues
and Mailboxes.** That belief was wrong, and undoing its consequences is the
whole job.

**Ray and this agent are restoring the UVM to its correct design.** Not
approximating it, not improving on it where the improvement costs a
capability — restoring it. D3 is the falsifiable form of *why the original
designers were not primitive*: a statically-typed language (SystemVerilog)
with a static alternative on hand still chose runtime indirection three
times — `mailbox#(T)` yet built TLM, typed classes yet built a factory,
parameters yet built a config DB. Three for three. The dynamism is
load-bearing, and calling it unsophistication is the exact error being
reversed.

**The disposition to watch for (this is the bias that caused the damage).**
The pull is: *"I can make this static, therefore I should."* It feels like
craftsmanship and it reads as an improvement in the moment. It is the thing
that deleted build/connect. D3 is the antidote but does not fire on its own —
a future session must apply it deliberately to any place it is about to
replace runtime indirection with a type. When in doubt, the UVM/pyuvm design
is presumed correct and the burden is on the static alternative to prove it
loses nothing.

### 0.3 The two things the UVM had that were destroyed

Stated plainly so a future session cannot miss the target:

1. **Dynamic component build and connect.** Components construct their
   children in a top-down `build` phase and wire them in a bottom-up
   `connect` phase. The *gap* between "a component exists" and "its children
   exist" is not overhead — it is where every late-binding mechanism lives
   (config, factory, TLM connection). R3 collapsed that gap into the
   constructor and called the gap waste. D5/D6 restore it.

2. **TLM FIFOs that encapsulate Queues and Mailboxes.** The UVM's
   `uvm_tlm_fifo` wraps a queue/mailbox so that two components connect to
   the *same FIFO* and **neither learns the other exists** — the FIFO is the
   point of decoupling, not an optional hierarchy ornament. rustdv already
   has `Queue` (a cocotb-queue port) and `TlmFifo` wrapping it, but the code
   currently frames the FIFO as "for when it should be visible in the
   hierarchy," which understates its job. The FIFO *is* the encapsulation
   that makes the connection late-bound (D17, D23, D24).

### 0.4 The typing thesis — why D3 is true

D3 is the rule; this is the argument behind it. It is the sharpest statement
of the project's reasoning, and a session that has only the rule will apply
it mechanically and miss the point.

**Ray's position, in his words.** He created pyuvm and *was proud of not
having typing in it*. Fable crowed about finding all bugs at compile time —
"but that was only because it did not implement UVM." When one implements
UVM correctly, heavy typing has some utility finding simple bugs early. But
the real UVM bugs are at runtime. Meanwhile the new user has paid a steep
learning curve to work with types when types only provide part of their
value.

**The decisive exhibit is SystemVerilog's own config DB.** SV *did* apply
heavy typing there: `uvm_config_db#(T)` is parameterized and the type flows
into the lookup (D65). What did it buy? Not safety — a *bug class*. The
`int`/`bit`/`uvm_bitstream_t` mismatch, where `set` and `get` never meet and
the failure is a silent `return 0` indistinguishable from "never set." The
type parameter supplies the appearance of type safety while correlating
nothing between the write and the read (D14). Dropping it, as pyuvm did,
removes the failure mode outright. Typing there is not neutral; it is net
negative.

**And there is a structural reason, not merely an empirical one.** A type
system can only check what is known statically. The entire purpose of the
configuration layer, the factory, and TLM connection is to *defer* decisions
to runtime so that one environment serves many tests. Static checking is
therefore definitionally excluded from precisely the layer where UVM's
complexity concentrates. D22 states a narrow case — "late binding and static
completeness are mutually exclusive" — and it generalizes to the whole
late-binding surface.

So Fable's compile-time claim was not a discovery about Rust. It was an
artifact of having deleted the runtime decisions: remove late binding and of
course everything becomes statically decidable. It had built a testbench
compiler, not a verification framework. Q16 is the same error still
unresolved — `AluEnv<T>` cannot express Chapter 30, because a factory
override cannot reach a type parameter.

**The honest counterweight, so this is not read as "typing is a tax."**
Types did real work on this branch, twice, and neither case was a simple
bug. The `'static` bound on `spawn` refused an unsound concurrent-run design
— a borrowed component tree handed to a task that outlives it, which in C++
is a use-after-free found weeks later (D56, D59). `async fn` in a trait
costing dyn-compatibility forced an architectural decision immediately
rather than at integration (D48). Note what both concern: **memory and
ownership**, not binding.

**Hence the principle, which is D3 with the seam made explicit:**

> Types for data and ownership. Runtime indirection for topology and
> binding.

rustdv already splits this way — transactions are plain structs with derives
(R1), sharing is `Rc`/`RefCell`, lifetimes are checked hard; while config,
factory and TLM are dynamic. SystemVerilog has a type system too; it simply
declined to use it for late binding. That is D3's three-for-three observed
from the other side.

**Two justifications for Rust that survive all of the above**, and should
not be confused with bug-finding: the value of types scales with codebase
and team size (a fifty-component testbench refactored by four people gets
something a five-hundred-line pyuvm testbench does not), and
monomorphization with no GC is the *emulation* argument (D36), which is
about throughput, not correctness.

**Consequence for the book.** The learning-curve objection is a product
argument and D38's two front doors is the only answer to it: a reader must
be able to write a complete, useful testbench with a DUT handle and signals
and no `Component` at all. If Part II ever becomes a stepping stone rather
than a destination, the curve argument wins and rustdv loses the FPGA
audience.

## 1. Method
**D1. Code before prose.** The original failure was a design question settled
in an essay (OQ-9 "retired — the question no longer exists") with no
prototype. Order is now: write the aspirational example → make the framework
satisfy it → Fable writes the chapter from working code.

**D2. Examples are the specification.** Book examples are modified first and
must compile and run. `book-sync` already enforces that the book matches them.

**D3. Detection rule for future cuts.** *Where a statically-typed language
with a static alternative available still chose runtime indirection, the
indirection is load-bearing.* SystemVerilog had `mailbox#(T)` and built TLM
anyway; had typed classes and built a factory; had parameters and built a
config DB. Three for three.

**D4. Disclosure rule.** Any open question closed with "no longer exists"
must name what the deleted thing was *for* and say where that need now
lives — or record it as unmet. OQ-14 is the model ("the usability risk did
not vanish — it transferred into the traversal derive macro").

## 2. Hierarchy and lifecycle
**D5. Restore `build` (top-down) and `connect` (bottom-up).** The gap
between "a component exists" and "its children exist" is where all late
binding lives. Chapter 24's "one-pass construction has no gap for them to
fill" described the feature as though it were waste.

**D6. Two-stage construction.** A component is constructed, then populated
in `build`. Children are `Option<T>` (or `Vec<T>`). This gives back a
"declared but not yet built" state — the same one SystemVerilog has as a
null handle — and Chapter 13's "nothing is ever half-built" claim must be
amended rather than defended.

**D7. Identity is derived, never stored.** No parent pointer: the parent
owns children as fields, so a back-pointer is a cycle requiring `Rc`/`Weak`.
No stored name or path field either — the current hand-typed
`Logger::new("env.loga")` strings are unverified and silently lie when a
component moves. The walk accumulates the path and hands it down.

UVM needs `m_parent` for `get_full_name()` (we compute it), `get_parent()`
navigation (we reject it), and child registration (ours is structural). It
buys nothing we cannot get otherwise.

~~**D8. One context type per phase** — `BuildCtx`, `ConnectCtx`, `RunCtx`.
Each phase's legal operations are encoded in its type: `build_child` does
not exist on `RunCtx`, so adding a component during run *fails to compile*.
UVM catches the analogue at run time ("Attempt to connect … at or after
end_of_elaboration. Ignoring.").~~

**Struck 2026-07-21 — superseded by D47.** There is one universal
`RustdvCtx`. The compile-time guarantee D8 bought is real and is genuinely
given up: phase-illegal operations are now caught at run time, as UVM
catches them. The reason is D38. Part II teaches a testbench with no
components and therefore no phases; handing that reader a type named for a
phase names a concept the book has not introduced, and the alternative
(`BuildCtx`/`ConnectCtx`/`RustdvCtx`) is an inconsistent family. One
context, one name, taught once.

**D9. The context is cloned per node**, carrying the accumulated path:

```rust
fn child(&self, name: &str) -> BuildCtx<'a> {
    BuildCtx { path: format!("{}.{}", self.path, name), rt: self.rt }
}
```

Services therefore sit behind a *shared* reference, not `&mut` — which also
means `ctx` need not be `&mut`, removing a class of borrow conflicts.

**D10. `ctx` carries identity; the store is ambient.** pyuvm's signature
already encodes the split: `ConfigDB().get(self, "", "MSG")` — ambient store,
identity passed in. The half rustdv lacks is the identity.

## 3. Configuration
**D11. `ConfigDb` is an ambient (global) resource.** Forced, not stylistic:
components read configuration at any time → therefore from code outliving
any phase → spawned tasks require `'static`, so no borrowed context → an
owned handle threaded everywhere is the plumbing tax again. A `thread_local!`
is safe because the executor is documented `!Send`, "it never leaves the sim
thread." rustdv already has an ambient service and does not admit it:
`log::info(...)` is a free function reaching a global sink.

**D12. `get()` takes a context and a concrete path; `set()` takes a glob**,
both relative to the caller's position. pyuvm enforces this — wildcards are
legal only when storing.

**D13. Three-tier resolution**, in order:

1. most specific matching path wins;
2. then highest precedence — `default_precedence - depth` during build, so
   the shallowest setter wins regardless of write order; run-time writes use
   `default_precedence` and outrank all build-time writes;
3. then most recent write.

Tier 2 is load-bearing and cannot be dropped: build is top-down, so an
ancestor writes *earlier* than a descendant, and "last write wins" alone
would invert the expected result.

*Divergence to state in the book:* SystemVerilog does not sort by
specificity at all — `get()` gathers every regex match and takes the highest
precedence. Specificity-first is pyuvm's rule. We keep pyuvm's.

**D14. Failure is loud.** SV's `get()` collapses four distinct failures —
never set, path mismatch, field typo, *type mismatch* — into `return 0`,
leaves the `inout` value untouched, and returns a discardable `bit`. That is
the silent zero. Ours returns `Result` with a distinguishing error, marked
`#[must_use]`, returning an **owned value** so no borrow into the store is
held across a call into user code.

SV's config DB is type-*parameterized*, not type-*safe*: `T` filters a
runtime lookup and nothing correlates a `set` with a `get`. Rust's
contribution here is error clarity, not typing.

**D15. Typed keys are an ergonomic option, not the mechanism.** File-driven
testbenches have open-ended knobs with no compile-time Rust type, and
`TypeId` cannot distinguish two `u32` knobs on one component — which is why
UVM has a field name. String keys stay first-class.

**D16. The runner clears the store between tests.** A singleton persists
across tests in one process; pyuvm has `ConfigDB().clear()` for exactly this.

## 4. TLM
**D17. Ports live in components; exports live on FIFOs; FIFOs are
components** instantiated beside the components they connect, as children of
the parent. A connection is always *port → export*, never component →
component. Two components communicate by connecting to the same FIFO and
neither learns the other exists.

**D18. The capability zoo becomes traits; the names become type aliases.**
~9 primitive traits (put/get/peek/transport × blocking/nonblocking, plus
analysis); composites are one-line supertraits with blanket impls; port
names are `type` aliases over a single `Port<I>`. Nothing multiplies except
names.

**D19. Full name parity.** Ship every UVM port name. API completeness and
curriculum are separate decisions — the book teaches the common subset and
notes the rest exist. An engineer who greps for `get_peek_port` and finds
nothing concludes the framework is thin.

**D20. `_imp` classes are not ported.** They exist only because
SystemVerilog lacks multiple inheritance; a Rust component simply
`impl Put<T> for Scoreboard`.

**D21. `m_if_mask` is not ported.** UVM checks interface *subsetting* at run
time with a bitmask because SV cannot express "provides at least this
capability set." Supertrait bounds do it at compile time.

**D22. Cardinality is checked at elaboration**, reporting every unconnected
port at once — not lazily at first use (pyuvm) . This is `resolve_bindings`'s
min/max check, and it cannot be a compile-time check: late binding and static
completeness are mutually exclusive.

**D23. FIFOs keep their built-in `put_ap` / `get_ap` analysis taps.**

**D24. FIFOs expose separately-named export objects** so each has a path and
appears in the hierarchy; only the blocking/nonblocking/peek combinatorics
collapse into traits.

## 6. Chapter 23 specifics
**D26. No factory in Chapter 23.** The book does not use it there; it
arrives in Chapter 29.

**D27. `#[rustdv::test]` annotates a struct or type alias**, registering the
component by name so the runner can `run_test("random_test")` — UVM's
`run_test()` restored. It no longer annotates a free function.

**D28. Shared behavior is a generic base, not inheritance-by-composition.**
`AluTest<T: Tester>` is written once; `RandomTest` and `MaxTest` are type
aliases. "Extends, overriding one thing" becomes "a type alias for a generic
base." The varying type is a real field, so no `PhantomData` and no marker
object — holding an object to carry behavior is a SystemVerilog reflex.

## 7. Repository conventions
**D29. No source file is named `lib.rs` — this is a general rule, not just
for chapter crates.** A crate root is named after the crate
(`path = "src/ch23_uvm_test_testbench_3_0.rs"`); a module file is named
after the module. Identical `lib.rs` files across dozens of crates are
unsearchable and unreadable in an editor tab bar — the same defect that
moved the Rust community off `mod.rs` in 2018. Ray states this as settled
practice: `lib.rs` was tossed aside long ago, do not reintroduce it.

*Migration status (2026-07-21):* applied to ch23. **Not yet applied** to the
framework crates (`rustdv-uvm/src/lib.rs`, `rustdv-sim/src/lib.rs`,
`rustdv-runner/src/lib.rs`, `rustdv/src/lib.rs`, etc.) or the quarantined
chapter crates (ch18–ch39 still ship `src/lib.rs`). Convert each crate's
root as it is next touched, setting `path` in its `Cargo.toml`. D31 applies:
a rename moves `file:line`, so it must precede that crate's transcript
regeneration.

**D30. Do not split Part II chapters by figure.** Part I figures are
standalone programs — one file each is right. A Part II chapter is a single
testbench built from interdependent figures.

**D31. Renames precede transcript regeneration.** Log lines embed
`file:line`, so every rename touches every transcript that shows a log
message.

---

**D32. Rust naming convention wins: `ConfigDb`, not `ConfigDB`.** Matches
`HashMap`, `TcpStream`, `Utf8Error`.

**D33. The BFM is not a component** — it is the analogue of a SystemVerilog
virtual interface, not a hierarchy participant. It stays a plain field,
shared by `Rc`, with no path and no phases.

**D34. Phase traversal follows pyuvm, not SV UVM.** So: `build` top-down,
`connect` bottom-up, `run` bottom-up, and `end_of_elaboration`,
`start_of_simulation`, `extract`, `check`, `report`, `final` all top-down.
SV UVM makes the middle five bottom-up. The book must state the divergence
plainly rather than let a reader assume 1800.2 behavior.

**D35. This document does not become the architecture documentation.** It is
a changing decision log with no teaching structure. Architecture
documentation is a separate document, written once the design settles.

## 8. Emulation
**D36. Emulation is a Day-1 target, not a later port.** In co-emulation the
DUT runs in hardware at MHz while the untimed side runs UVM in a simulator —
so the *software side is very often the bottleneck*. A compiled,
monomorphized, GC-free testbench attacks exactly that bottleneck, and an
order of magnitude on the untimed side changes the economics of owning an
emulator. This is plausibly rustdv's largest opportunity.

**D37. The BFM is the portability boundary.** Above it — sequences,
scoreboards, coverage, configuration, factory — is untimed and portable.
Below it is either software pin-wiggling (simulation) or a synthesizable
transactor (emulation). One testbench, two deployments.

**D38. Two audiences, two front doors, both first-class.** rustdv must serve
the *timed* world of FPGA engineers (signals, clocks, pins — cocotb-shaped,
no components required) and the *untimed* world of emulation engineers
(transactions only). **The component layer is optional.** A complete, useful
testbench must be writable with a DUT handle and signals and no `Component`
at all. Part II stays a legitimate destination, not a stepping stone.

**D39. Timed/untimed separation is convention, not compiler-enforced.**
Emulation engineers can be trusted to follow it. *(Rejected: giving untimed
components a restricted context so they structurally cannot reach a signal.
It taxes the FPGA majority to serve the emulation minority.)* Consequence:
DUT access stays universally available on the context — `ctx.dut()` is fine.

**D40. Clock generation is a convenience, not infrastructure.** `Clock`
stays in rustdv for those who want it, but it is not the recommended path
and rustdv never generates a clock implicitly. **BFMs wait on edges; they
never drive them** — which is what makes a BFM port to an emulator unchanged.

**D41. Clock generation belongs in `run`, not `build`.** It is an activity,
not structure, and a task started during `build` runs before any objection
exists. cocotb does the same: `start_soon(Clock(...).start())` in the test
body.

## 10. Step 4 — the context and the test macro (2026-07-21)
**D46. `#[rustdv::test]` accepts both a free `async fn` and a struct.**
*(Resolves Q13; amends D27, which said the macro no longer annotates a free
function.)* The two forms map onto the two source books — `@cocotb.test()`
decorates a coroutine *function*, `@pyuvm.test()` decorates a *class*. This
is D38's two front doors made concrete, not a concession to avoid breaking
ch15–ch21. They unify rather than fork the framework: the `fn` form's shim
and the struct form's shim both produce the same erased future, so there is
one registry and one execution path behind two syntaxes.

**D47. There is one universal context, `RustdvCtx`.** *(Resolves Q14;
strikes D8.)* It carries the DUT handle, the seed and RNG, the objection
registry, and the component's path. It is `Clone`, with the objection
registry `Rc`-shared, which is also what D9's per-node clone needs when the
build phase arrives in ch24.

The cost is stated plainly because the book must state it: phase-illegal
operations are no longer compile errors. `build_child` during run will be a
run-time failure, which is exactly UVM's behavior and *not* the Rust
advantage ch24 was going to claim. The gain is that Part II — which has no
components and therefore no phases — is not handed a type named after a
phase it has not met.

**D48. Async in the trait costs dyn-compatibility, so the sync phases move
to a separate trait.** `Component::run` is an `async fn` in a trait, which
makes `Component` not dyn-compatible; since `ComponentNode` had it as a
supertrait, `&mut dyn ComponentNode` stopped compiling. The sync phases
(`extract`, `check`, `report`, `final_phase`) therefore live on a dyn-safe
`Phases` trait with a blanket impl over every `Component`, so users still
override them on `Component` and the traversals still walk `dyn`.

`run` itself is static-dispatch and boxed only at the registry boundary.
The consequence to face in ch24: a bottom-up `run` traversal over a tree of
`dyn` children needs boxed futures at that boundary too. Not decided here.

**D49. The root path is the test's registered name.** UVM names it
`uvm_test_top`; ours logs `[random_test]`. The name a reader typed is more
useful than a fixed sentinel, and D7 makes paths derived, so the root is
simply where the walk starts. Divergence to state in the book.

**D50. Superseded doc comments are a disclosure failure, and get marked in
place.** The framework's own doc comments asserted R3/R4/R5 — build/connect
as constructor conventions, config as constructor arguments, variation
points as constructor injection, "no factory" — flatly, as settled design.
That is D4's rule broken inside the source: a reader (human or a later
session) opening `rustdv-uvm/src/lib.rs` top-down would take the
closed-world design for the intended one, exactly the way OQ-9's "the
question no longer exists" hid the original loss.

The rule from here: **a doc comment describing a reversed decision is
marked superseded where it sits, naming what reverses it and whether the
replacement has landed** — not deleted (the code still does what it says)
and not left bare. Marked so far: `rustdv-uvm/src/lib.rs`,
`rustdv-uvm/src/component.rs`, `tinyalu_tb/src/env.rs`,
`rustdv-macros/src/lib.rs`. R1, R2 and R6 stand and are marked as standing,
so the distinction stays visible.

## 11. Chapter 24 — the phase lifecycle restored (2026-07-21)
**D51. The nine UVM phases return as real trait methods, and the runner
drives them.** This reverses the R3 damage directly: `build` and `connect`
were destroyed, demoted to "constructor conventions," leaving rustdv with
no phase gap for late binding to live in. The full set, in pyuvm order
(D34), each a `Component` method with a default no-op body:

| # | phase | direction | notes |
|---|-------|-----------|-------|
| 1 | `build` | top-down | constructs children (D6); the gap late binding needs |
| 2 | `connect` | bottom-up | wires children |
| 3 | `end_of_elaboration` | top-down | |
| 4 | `start_of_simulation` | top-down | |
| 5 | `run` | bottom-up | async, objection-gated (ch23's `run`) |
| 6 | `extract` | top-down | |
| 7 | `check` | top-down | takes `&mut CheckSink` |
| 8 | `report` | top-down | |
| 9 | `final_phase` | top-down | |

The runner runs this whole sequence over the component tree — the analog of
pyuvm handing the class to its phaser. A `#[rustdv::test]` struct therefore
needs **no** hand-rolled `start_all`/`run_extract_check_report`; the ch23-era
scaffolding in test bodies goes away. `run`'s bottom-up traversal over `dyn`
children is where D48's boxing question comes due.

**D52. Every phase receives the context (`&mut RustdvCtx`), including the
post-run phases.** Today `extract`/`report`/`final_phase` take nothing and
`check` takes only a `CheckSink`. The phase-logging example is the reason
this is wrong: each phase must log with the component's *path* (D7), so each
needs the ctx the walk derived. This changes those four signatures — a
framework change and a `tinyalu_tb` update, since it is the only
non-quarantined consumer of the old shapes.

**D53. `build`/`connect` restore R3's amendment.** The framework doc
comments (`rustdv-uvm/src/lib.rs`, `component.rs`, `tinyalu_tb/src/env.rs`)
marked R3 "reversed, not yet implemented." D51 implements it. When the
framework increment lands, those markers change from "reversed, pending" to
"restored," and the R3 constructor-convention text is struck, not left
dangling.

**Naming note (minor, not blocking).** Eight phases are bare verbs (`build`,
`connect`, …) and one is `final_phase`, an inconsistency inherited from
before step 4. `final` is a Rust reserved word, so the suffix on that one is
forced; the others stay bare. If full UVM `*_phase` parity is ever wanted
for the book's SV-UVM audience, it is a mechanical rename, decided then.

- **D54. `children_mut()` replaces `visit_children` as the child primitive.**
  `ComponentNode::children_mut(&mut self) -> Vec<(String, &mut dyn
  ComponentNode)>` returns an owned Vec of the children. The old sync
  callback could not support an async traversal: a higher-ranked
  `FnMut(&str, &mut dyn ComponentNode)` erases the child lifetime, so a
  child borrow cannot escape the call into a Vec or across an `.await`.
  Returning owned borrows fixes both, and it reads better — every traversal
  is now a plain `for (name, child) in node.children_mut()`. The derive,
  all traversals, `print_hierarchy`, and `TlmFifo`'s hand-impl moved over.

  child borrows across the awaits, which `children_mut` makes legal.
  `run_component_test` now calls `run_all`, so every component's run fires,
  not just the top's.
- **D56. Run is sequential, not concurrent — recorded, not hidden.** Each
  `run` is awaited to completion before the next. This is correct while run
  bodies are self-contained (raise objection → act → drop), which is the
  shape at ch24 and in `tinyalu_tb` (whose persistent work lives in the
  `start` spawn hook). True concurrent run phases need spawned `'static`
  tasks, and `rustdv_sim::spawn` is `'static`-bound, so a borrowed-tree
  concurrent run is a genuine later increment — not a thing to fake with a
  join over boxed futures that still can't outlive the tree. Flagged so the
  concurrency is restored deliberately when a testbench first needs two
  long-running run phases at once.

**D57. The BFM is ambient — Q11 resolved, and Q12 deferred to ch27.** At 4.0

**D58. Singletons are per-test, and the framework owns the clearing.**
`rustdv-uvm/src/singleton.rs` ports pyuvm's `Singleton` metaclass:
`singleton::<T>(init) -> Rc<T>` over a `thread_local` `TypeId` map, plus
`clear_singletons()`. The runner calls it before every test, matching

rule generalized past the ConfigDb. The store is deliberately not borrowed
across `init()`, since a constructor may reach for another singleton.

**D59. `'static` is why spawned collectors clone `Rc` handles.** The
scoreboard's monitor tasks are spawned in `start_of_simulation` and must be
`'static`, so they cannot borrow `self`. They clone `Rc` handles — the task
owns a refcount, not a borrow. This is the same constraint that blocks a
concurrent `run` traversal (D56), and 4.0 is where the book first shows the
pattern that works around it.

**D60. The objection is currently decorative, and the book must not claim
otherwise.** Caught while correcting a comment: in UVM and pyuvm the
objection is what *ends the run phase* — run phases are forked and the phase
completes when the last objection drops. In rustdv as built, `run_all`
awaits each component's `run` sequentially (D56), so the phase ends when the
tester's `run` returns. The objection is raised and dropped inside that
call, and `all_objections_dropped()` afterwards finds `count == 0` and
returns immediately.

So the objection is written the way UVM writes it, and it is *inert*. It
becomes load-bearing the moment run phases are concurrent — which is exactly
the increment D56 defers — and it is already load-bearing for a run body
that hands an objection to a spawned task. But at ch25 nothing does that.

Two consequences, both recorded rather than papered over:

1. **Prose rule.** No chapter may say the objection "holds the run phase
   open" until concurrency lands. The honest line is: the objection is how
   UVM ends the phase, rustdv will match that, and today the sequential
   await is what sequences things.
2. **This is a capability gap, not a simplification.** It belongs with D56
   as one item: concurrent run phases + meaningful objections arrive
   together, because neither is worth much alone.

**D61. Spawning in `start_of_simulation` is correct, not a shortcut.**
Raised as a challenge — "in UVM and pyuvm only `run_phase` can be threaded"
— and worth settling in writing so nobody "fixes" it later.

The UVM rule is that only `run_phase` may **consume time**. Spawning does
not: `spawn_named` schedules a task and returns, exactly as
`cocotb.start_soon` does in the Python original (chapter 29, Figure 5,
titled *"Using the start_of_simulation_phase() to launch the monitoring
tasks"*), and as `fork...join_none` does in a SystemVerilog function. The
phase still completes instantly, so the rule is not broken.

And there is a positive reason, not just permission: `start_of_simulation`
completes across the *entire tree* before any `run` begins, so the monitors
are provably listening before the first stimulus. Spawning them in `run`
races the tester for the first transaction — in pyuvm because run phases are
forked together, and in rustdv today (D56, sequential run) because
correctness would silently depend on **child declaration order**
(`scoreboard` before `tester` in `AluEnv`). Order-dependent correctness is a
bad thing to teach.

Recorded in the example itself with a "do not correct this into `run`" note.

**Verified not vacuous.** With `alu_prediction`'s XOR sabotaged to OR, both

## 14. Chapters 27–28 — configuration, the ConfigDb, and debugging it

**D65. One namespace per (path, field) — the type is not part of the key.**
This is a real behavioural divergence from SystemVerilog, and the chapter
must state it rather than let a reader assume 1800.2 semantics.

*SystemVerilog namespaces by type.* `uvm_config_db#(T)::get` passes the type
handle into the lookup as a filter (1800.2-2020,
`src/base/uvm_config_db.svh`):

```systemverilog
rq = rp.lookup_regex_names(inst_name, field_name, uvm_resource#(T)::get_type());
r  = uvm_resource#(T)::get_highest_precedence(rq);
if (r == null) return 0;
```

So `uvm_config_db#(int)` and `uvm_config_db#(bit)` at the same path and
field name are genuinely separate entries. When a `set` and a `get`
disagree on type, the lookup simply finds nothing and returns 0 —
indistinguishable from "never set." This is the classic `int` / `bit` /
`uvm_bitstream_t` mismatch, and it is one of the four failures D14 calls the
silent zero.

*pyuvm does not namespace by type.* Its ConfigDB is, in its own words, "a
dual-level dict" — outer keyed by path (glob-matching), inner by field name
— and "unlike the UVM config_db, this config_db makes no effort to store
multiple items at one location. The last stored wins."

*rustdv follows pyuvm, and makes the mismatch loud.* An entry is found by
(path, field); the type is checked on read and a mismatch is its own error,
naming the type stored and the type requested. That is only expressible
because the type is *not* in the key — under SV's scheme a mismatch is
unfindable by construction, so it cannot be reported. D14's summary stands:
"SV's config DB is type-parameterized, not type-safe... Rust's contribution
here is error clarity, not typing."

**What this costs, stated plainly (D3/D4).** Two *different* types can no
longer coexist under the same field name at the same path. SystemVerilog
allows that; rustdv's last-write-wins will overwrite, and the loser's `get`
reports a type mismatch. We judge the SV behaviour a footgun rather than a
feature — it is the very mechanism by which a `set` and a `get` silently
fail to meet — but it *is* a capability SV has and we do not, and it is
recorded here as a loss rather than dressed up as an improvement.

*Book note:* state this beside D13's other divergence (specificity-first
resolution is pyuvm's rule, not SV's).

**D66. `get` and `set` take a context, an offset and a field — the
signature is the mechanism.**

```rust
ConfigDb::get(Some(ctx), "",     "MSG")?    // zero offset — the caller
ConfigDb::get(Some(ctx), "loga", "MSG")?    // on behalf of a child
ConfigDb::get(None,      "",     "SEQR")?   // no context — a sequence
ConfigDb::set(Some(ctx), "env.t*", "MSG", v);
ConfigDb::set(None,      "*",      "MSG", v);
```

*This reverses a design proposed in this session and is recorded because
the reversal is instructive.* The proposal was `ctx.config_get("MSG")` — no
context, no offset — reasoning from D10 that the context already carries
identity, and from ch26 that a path argument is noise. Ray rejected it.
Two capabilities were being deleted:

1. **Non-components could not read.** A `Sequence` is not in the component
   tree and has no path; it receives a `SeqCtx`, not a `RustdvCtx`. In the
   Python book, `TestAllSeq`, `TestAllParallelSeq` and `FibonacciSeq` all
   call `ConfigDB().get(None, "", "SEQR")`. TB 7.0, 7.1, 7.2 and 8.0 all
   depend on it. Under the proposal the call is not awkward, it is
   *uncallable*.

2. **Nobody could read on behalf of another path.** `""` is not a keyword
   meaning "me" — pyuvm resolves it as `context.get_full_name()`, so it is
   an **empty offset** that happens to land on the caller. A non-empty
   offset is a lookup on behalf of another component: a parent reading the
   parameter destined for each child, matching it, adapting it, re-setting
   it downward. The proposal collapsed a general addressing scheme into its
   one degenerate case.

**Neither book's examples ever pass a non-empty offset to `get`** — every
call is `""` or `"*"` — and both languages kept the argument anyway. That is
D3 in a subtle form: the mechanism is deliberately more general than
anything that exercises it, and the generality is the point.

*Why relative and not absolute.* An offset resolves against a context, so a
lookup is position-independent. An absolute path would be the hand-typed
string D7 forbids — it keeps compiling and starts lying the moment a
component moves. Relative addressing therefore *requires* the context
parameter; it is not ceremony around the mechanism, it is the mechanism.

*Method note.* The ch27 example would not have caught this: every reader in
that chapter is a component reading its own path, so the design compiles and
looks right, and fails at ch36. **An aspirational example only protects the
design as far as the example reaches** — when an API is being settled, check
it against the chapters that come after, not just the one being written.

Any `ctx` convenience wrapper is sugar over this signature and must not hide
the offset.

**D67. Copy or share is the user's choice, made at the `set` call.** The
rule, as the book states it:

> A value you store in the ConfigDb must either implement the `Clone` trait
> so that everyone gets their own copy, or be wrapped in an `Rc` so that
> everyone gets a handle to a single copy.

`MSG` is a `String` and each logger wants a copy. A sequencer is not: at
ch36 every sequence must reach the *same* sequencer, so it is stored as an
`Rc`. Implementation-wise this is a single bound (`T: Clone + 'static`),
because `Rc<T>` is `Clone` whatever `T` is — but that is framework trivia
and is deliberately **kept out of the prose**.

*Why the phrasing matters.* The first draft of this note led with the trait
mechanics — "one bound, and `Rc` is how you satisfy it" — and Ray cut it:
"Rc actually being a clone is a technical nit. It makes no difference to the
newbie user." He is right, and it is §0.4 in miniature: the reader's
question is semantic (copy or share?), and answering it with trait-bound
mechanics charges learning curve for nothing. Two choices, two consequences,
made at the `set` call is the whole of what a reader needs.

*Known rough edge, worth a sentence when the chapter is written:* storing a
non-`Clone` type unwrapped produces `the trait bound X: Clone is not
satisfied`, which names the symptom and not the fix.

**D68. ch28 changes shape: from compile-fail figures to a sim chapter.**
The chapter as inherited was **four programs asserting that configuration
bugs are compile errors** — the purest surviving artifact of the belief
§0.4 dismantles, and worth quoting before it is deleted:

| old figure | claim | mechanism |
|---|---|---|
| 1 | "The 'wrong path' mistake is now a wrong name" | `E0560` — misspelled struct field |
| 2 | "The 'wrong type' mistake never reaches runtime" | `E0308` |
| 3 | "Forgetting to configure is a missing field" | `E0063` |
| 5 | "The debugging that remains — print the config tree" | one `derive(Debug)` |

ch27 carried a matching one: *"Figure 10: The parent/child conflict has
nowhere to live."*

**Why these do not prove what they claim.** Figure 1 demonstrates a "wrong
path" by misspelling a *struct field*. A wrong path in a config database is
`"env.loga"` versus `"env.logA"` — a string, resolved at run time, that no
compiler will ever check. The figure substituted an easier problem and
declared the harder one solved. Figure 10 is the same move: the conflict has
"nowhere to live" only because the mechanism that hosts it was removed. And
"the debugging that *remains*" concedes the frame — debugging had not been
abolished, it had been made impossible to demonstrate.

*Action taken.* `ch27-configuration/compile-fail/` and
`ch28-config-debugging/{compile-fail,src/bin}` deleted (git retains them),
removed from the examples workspace members, and ch28 converted to a cdylib

were **not** wired into the regression — `manifest.json` covers only Part I
— so nothing was verifying them anyway.

*For the book:* ch28 is now the chapter where the reader learns that late
binding costs you compile-time checking and buys you a debugger's toolkit
instead. That trade is the honest version of what these figures denied.

**DONE (2026-07-22). ch27 and ch28 run green on Icarus.** ch27's four tests
resolve per-path, wildcard, global and conflict correctly; ch28's seven

- `TestError` gained a `kind`, `Outcome::Fail` carries it, and

- `ConfigDb::clear()` joins `clear_singletons()` and `log::reset_config()`

**Two findings worth keeping.**

*Precedence is scaled by the depth of the **setter**, not of the path

## 15. Chapters 29–30 — the factory, and why rustdv does not port it

Design settled with Ray on 2026-07-22, before code. The factory is where
D3 pays off in reverse: the honest Rust answer is *not* a faithful port.

**The factory fused two problems (Ray's framing).** UVM's factory solves two
distinct needs with one mechanism:

- **A — substitution.** "Everywhere, or at this path, you build a dog, build
  a cat instead," without editing the code that builds it. Historically the
  aspect-oriented language `e`/Specman did this as cross-cutting
  replacement; the OO factory is the workaround for a language without
  aspects. The essence is *decoupling the decision (top of the hierarchy)
  from the instantiation site (deep in it)*.
- **B — string→object.** Read names from a file and instantiate by string.
  The set of names is *data*, unknown at compile time.

They have different Rust answers, and only B needs a registry.

**D69. The override surface is a published contract, not a universal
capability. This is a deliberate reversal of the UVM factory default.** Two
schools exist: build every component through the factory ("someone might
want to change it"), or build only the *changeable* ones through it. Ray's
rule, and rustdv's: the second. In his words — *"I'm not going to let some
idiot break my code and have me in on a weekend."* A block developer hands
the reuse user a **published list**: these component types you may override,
these instances you may override. Control of the override surface belongs to
the block author, not to whoever imports the block.

UVM's type-keyed factory does the opposite: a `set_type_override(BaseTester,
…)` reaches *every* site that builds a `BaseTester`, automatically, whether
or not the author intended that site to be swappable. That automatic,
universal reach is precisely the liability D69 rejects. Closed by default,
open by published design.

**D70. Component substitution is a maker closure delivered through the
ConfigDb, keyed by a developer-published field name. rustdv has no component
factory.** The block author writes, at the instantiation site,
`let tester: Box<dyn Tester> = (ConfigDb::get::<Maker>(Some(ctx), "",
"tester_maker")?)();` and *documents* `tester_maker` as an override key. The
test at the top stores a maker: `ConfigDb::set(ctx, "*", "tester_maker",
make_random)`. A constructor is just a value.

This is not a new mechanism — it is the ConfigDb (§3, §14) with a closure as
the value. Consequences:

- **The trait match is checked at compile time.** `make_random: fn() ->
  Box<dyn Tester>` will not compile unless `RandomTester: Tester`. No
  `$cast`, no null handle, no run-time type failure on this path — strictly
  stronger than SV's factory, whose override type-safety is a run-time
  `$cast` (see §0.4).
- **Instance-vs-type override falls out of D13 for free.** `set(None, "*",
  …)` is the global (type) override; `set(ctx, "env.tc1", …)` is the
  instance override; specificity-first resolution makes the specific path
  win. UVM needs two separate calls (`set_type_override`,
  `set_inst_override`); rustdv gets both from the config resolution already
  built.
- **The key is the field name, not the type** (Ray's choice). Type-keying
  would be more automatic but is exactly D69's liability — it reaches sites
  the author never published. Field-name keying makes the override surface
  an explicit, documented contract and reuses the ConfigDb's published-knobs
  model: a block's reuse interface is "here are my ConfigDb keys," some
  `u32`, some makers. One mechanism.
- **No narrowing cast.** The maker returns exactly the trait the site needs
  (`Box<dyn Tester>`), so the dyn→dyn cast that has no direct Rust form never
  arises. There is no universal component base to traffic in and `$cast` out
  of, because there is no factory in the middle.

*Cost, stated (D4):* chained overrides (A→B→C, which the UVM factory
resolves transitively) are not expressed — a maker stores a final
constructor, not a type-to-type edge. Judged not worth the machinery;
recorded as a capability UVM has and rustdv does not.

~~**D71. The object factory — a link-time `name → constructor` registry —
survives for problem B only, and is deferred.**~~

**Struck 2026-07-22 — inconsistent with D69, corrected by D71 below.** Ray:
*"Wouldn't a text list of field names do the job?"* It does, and the
original D71 quietly reintroduced exactly what D69 rejects: an object
factory auto-registers *every* sequence type and lets a file name any of
them, which is the universal reach D69 refuses for components. Applying
"published contract, no universal registry" to components and then a
universal registry to objects one decision later was the error.

**D71. rustdv has no factory at all — string→object is also maker closures
in the ConfigDb.** A file of names is a list of *published ConfigDb keys*.
The block author publishes a maker per exposed sequence — `set(None, "*",
"fibonacci_seq", make_fibonacci)` — and reading the file is `for name in
lines { get::<Maker>(None, "", name)?() }`. The ConfigDb *is* the
name→constructor registry, populated by publication, not by automatic
link-time enrollment.

**Why UVM needed a separate factory and rustdv does not (the D3 point I
missed).** UVM keeps config_db and factory as two mechanisms because
**SystemVerilog constructors are not first-class values** — you cannot store
a constructor in the config_db, so the factory exists to hold `name → type`
and hand back a constructed object. Rust closures *are* first-class, so a
constructor is an ordinary stored value and the two mechanisms collapse into
one. Porting UVM's two-mechanism split would have been copying a workaround
for a limitation rustdv does not have.

*What is actually runtime here.* Only the *selection* is data — which key a
file line names. Every maker was published, and trait-checked, at compile
time. A line naming an unpublished key is a `ConfigError::NotFound`, which
is the correct answer (you may instantiate exactly what the block exposed),
not a failure mode to design around.

*Consistency check (D69):* components and objects now use one mechanism, and
the override/instantiation surface for both is the author's published set of
ConfigDb keys. No universal registry anywhere.

**Consequence for ch29–30.** ch29 (the factory's mechanism) becomes the
chapter that *introduces the maker-in-ConfigDb pattern* and says plainly why
rustdv does not have a `uvm_factory`. ch30 (TB 5.0): `AluEnv` holds
`Box<dyn Tester>` filled by a maker read from `tester_maker`; `RandomTest`
and `MaxTest` each store a different maker before building the env — which
is the ch25 `AluEnv<T>` type parameter (D28) replaced by a runtime override
point, exactly as Q16 anticipated.

**D72. Correction: "first-class values obviate registration" is false as
stated; pyuvm is the counterexample.** Ray: *"pyuvm registers components
automatically. If pyuvm needs registration, how can you claim rustdv does
not?"* Correct. D71's phrasing conflated two independent questions, and the
narrower truths are:

- **Is a registry needed?** Only for the *by-name* path (string →
  constructor), and then in *every* language, because a string is not a
  constructor regardless of first-class-ness. rustdv is no exception — the
  published makers in the ConfigDb *are* that registry, populated by hand.
  First-class values change only the *by-value* path, and only against
  SystemVerilog: SV cannot store a constructor, so `uvm_component_utils`
  registers a **proxy** (`type_id`) to stand in for the closure it cannot
  write. Python's class and Rust's closure *are* that value, so both skip
  the proxy — but that spares the by-type proxy, not registration as such.

- **Automatic-universal, or manual-selective?** pyuvm's metaclass enrolls
  *every* component; I claimed rustdv publishes *only what the author
  exposes* and called that a D69 consequence. **Both halves are wrong — see
  D73.** Registration should be universal, and D69 governs overridability,
  not registration.

~~So the defensible differences, precisely: (a) no by-type **proxy**
registry, versus SV, from first-class constructors; (b) **selective** rather
than universal registration, versus pyuvm, from D69; (c) **one store** rather
than two, because the makers live in config.~~ *(b) struck by D73.* The
surviving differences are (a) and (c); registration is universal like every
UVM.

*Where D70/D71 still stand:* the factory folding into the config store, the
compile-time trait check on the by-value path, and no separate `uvm_factory`
subsystem are all unaffected — they never depended on the registration
claim. Only the sentence "no mandatory registration *because* constructors
are first-class" is struck; read it as "selective registration *because of
D69*, plus no by-type proxy because constructors are first-class." *(And the
"selective" half of that is itself struck by D73 — registration is
universal.)*

**D73. Registration is universal, not selective — correcting D72(b).** Ray:
*"Selective registration is a mistake. It is just another error surface.
Every implementation of UVM has universal registration; why should rustdv be
different?"* Correct, and it exposes a conflation D72 still carried.

- **D69 governs overridability, not registration.** The author's control is
  the choice at the instantiation site: a child built with `create()` is
  overridable; a child built with `MiddleComp::default()` directly is not —
  which is UVM's own model (a `new()`'d component is not factory-swappable).
  Registration is orthogonal to that choice.
- **Selective registration is a pure error surface.** `create_by_name` for a
  type nobody remembered to publish fails at run time, for a type that
  plainly exists. Universal registration cannot fail that way and costs
  nothing, which is why every UVM does it.

So `#[derive(Component)]` enrolls **every** component automatically at link
time — the same section mechanism as `#[rustdv::test]` — mapping name→maker
(`|| Box::new(T::default())`) for all of them. Universal, free, no "forgot to
register."

The universal registry serves the **by-name** path (`create_by_name`,
by-name override, file-driven creation). The **by-type** path
(`MiddleComp::create()`) needs no registry: its default is a direct call and
its override a ConfigDb lookup.

**Consequence: rustdv has a factory, and the chapter should say so.**
Universal registry + override table + `create()` *is* a factory. ~~The
surviving differences from UVM are exactly three and all improvements... The
honest framing: here is rustdv's factory, and here is where it is better.~~
*(Struck by D74 — from the user's point of view it is the same, not better.)*
"rustdv has no factory" was the third false slogan (after "no factory as a
separate subsystem" and "no registration"); retire it.

**D74. From the user's point of view the factory is the *same*, not better —
correcting D73.** Ray: *"Would it be better from a user's point of view? I
argue it is the same."* Correct, and the "better" framing was the project's
own original sin in miniature — improving on UVM where UVM was right.

D73's three "differences" do not reach the user:

- Closures-vs-proxy and override-table-is-ConfigDb are **implementation**.
  The user adds a derive and calls `create()`, exactly as in SV (a macro and
  `type_id::create`) or pyuvm. Invisible.
- The compile-time override-type check **is** user-visible, but it catches a
  wrong *override type* — a bug found on the first run regardless. That is
  the low-value end of typing (§0.4); presenting it as an advantage repeats
  the "compile-time bugs" overclaim the branch exists to reject.

Versus pyuvm the experience is identical; versus SV it saves a `$cast` line
and turns a run-time null into a compile error — real but minor and
low-value. **Net: the same.**

And sameness is the *goal*. Restoring the factory means a UVM engineer gets
the factory they already know, spelled in Rust. The chapter reassures — *here
is the factory, it works as you expect, here is how you write it* — and does
not sell an improvement. Any place a future session is tempted to write
"rustdv's factory is better," check it against this: better *for whom*, and
on which of §0.4's axes.

**D75. The two constructors `new_comp()`/`create_comp()`, name-free; a child
field is always `AnyComp`; overridability is a flag on the slot, read by the
walk.** Settled with Ray across a long naming discussion (2026-07-22).

*The two constructors, transcribing the UVM/pyuvm pair.* Both languages use
one algorithm: build the normal way (`new` in UVM, `ClassName()` in pyuvm)
for a fixed component, and `create` for an overridable one. rustdv mirrors it
with `Foo::new_comp()` (fixed) and `Foo::create_comp()` (overridable). Both
take **no arguments** — the name and parent come from the tree (D7), not the
call. *(Rejected: `Foo::new()` for the fixed form. `new()` returning `AnyComp`
rather than `Self` is a Rust smell; `new_comp()` carries no such expectation.
Rejected: passing `"tc1"` to name an instance — it duplicates the field name
and can silently disagree, the footgun flagged earlier. Rejected: a bare
`Foo::default()` assignment — `default()` is the std trait and returns `Self`,
so it needs a `.into()` the `_comp` methods avoid. `default()` remains the
plumbing both call.)*

*The field type: `AnyComp`.* A child slot holds any component. The name went
through `Child`/`ChildComponent`/`ChildStruct`/`CompStruct` and Ray rejected
each: `Child` names a *position* in the tree, but position is not a property
of the type — any top-level component can be someone's child elsewhere (Ray:
*"If there is a Child is there a Top? Or a Parent?"*). `Component` is
correctly the trait. `AnyComp` names what the slot *holds* — any component —
which is always true and implies nothing about the hierarchy.

*Overridability is not in the type (Ray's rule).* **Every** child field is
`AnyComp`; the *build line* decides. `Foo::new_comp()` is fixed;
`Foo::create_comp()` is overridable. Figures 2 and 4 therefore have identical
structs and differ by one line — the clearest statement that overridability
is a choice, not a type. *(Rejected: fixed children keeping a concrete type
`Option<Foo>` while overridable ones are `AnyComp`. That made the field type
a policy badge; Ray: "there should be no difference in type for a fixed
child.")*

*How the walk resolves it — a flag, not a placeholder.* Ray: *"Why can't the
framework look at an `AnyComp` and tell whether it is resolved?"* It can, and
that deletes the deferred-placeholder machinery an earlier draft carried.
`create_comp()` builds the default component **now** and flags the `AnyComp`
as factory-owned; `new_comp()` builds it and leaves it un-flagged. During the
build walk — where the field name, and so the path, is finally known — the
framework inspects each child: if flagged, it checks the override table for
the component's type at that path (instance first, then type) and swaps in
the replacement before descending, so the discarded default's own
`build`/`run` never fire. `create_comp()` never needed the field name; it
builds the type it already knows, and the *override check*, the only part
that needs the name, happens at the walk. Cost: one cheap `default()`
possibly thrown away — negligible for a handful of components.

**Two consequences to carry forward:**

1. **Earlier examples should be retrofitted.** ch24/ch25 and `tinyalu_tb`
   store children as concrete `Option<T>`. "Always `AnyComp`" makes the book
   consistent only if those convert too — a mechanical but real sweep,
   deferred until after ch29–30 land.
2. **`AnyComp` is type-erased, so a parent cannot reach a child's concrete
   ports.** That is fine *only if* TLM connection goes through shared FIFOs
   (D17: port→export, "neither learns the other exists"), not by reaching
   into a concrete child. It aligns with D17–D24, but it must be verified
   when ch31–34 are built — if any pattern there needs a concrete child
   handle, "always `AnyComp`" has to be revisited.
