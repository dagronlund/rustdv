# Design decisions — the UVM restoration

Running record for branch `put_uvm_back_in_rustdv`. Every decision agreed
with Ray, with the reasoning that produced it, so a later session does not
re-litigate or silently reverse it.

**Append as decisions are made.** If a decision is reversed, strike it and
say why rather than deleting it.

> Provisional and internal while the refactor runs. Candidate for promotion
> to a public architecture document once it settles.

---

## 0. The premise

rustdv removed UVM's `build_phase` and `connect_phase` and, with them, the
entire late-binding surface: path-addressed configuration, factory
overrides, and TLM connection. Each removal was recorded locally as
"resolved by redesign"; the aggregate — that rustdv became a **closed-world**
framework, unable to configure or override anything you did not write —
was never recorded anywhere.

The book teaches rustdv as UVM-in-Rust, which creates a reader expectation
the framework does not honor. Restoring that capability is the point of
this branch.

**We are not bound by IEEE 1800.2.** Improve where Rust genuinely allows.
Do not lose capability while calling it an improvement.

---

## 1. Method

**D1. Code before prose.** The original failure was a design question settled
in an essay (OQ-9 "retired — the question no longer exists") with no
prototype. Order is now: write the aspirational example → make the framework
satisfy it → Fable writes the chapter from working code.

**D2. Examples are the specification.** Book examples are modified first and
must compile and run. `book-sync` already enforces that the book matches them.

**D3. Detection rule for future cuts.** *Where a statically-typed language
with a static alternative available still chose runtime indirection, the
indirection is load-bearing.* SystemVerilog had `mailbox#(T)` and built TLM
anyway; had typed classes and built a factory; had parameters and built a
config DB. Three for three.

**D4. Disclosure rule.** Any open question closed with "no longer exists"
must name what the deleted thing was *for* and say where that need now
lives — or record it as unmet. OQ-14 is the model ("the usability risk did
not vanish — it transferred into the traversal derive macro").

## 2. Hierarchy and lifecycle

**D5. Restore `build` (top-down) and `connect` (bottom-up).** The gap
between "a component exists" and "its children exist" is where all late
binding lives. Chapter 24's "one-pass construction has no gap for them to
fill" described the feature as though it were waste.

**D6. Two-stage construction.** A component is constructed, then populated
in `build`. Children are `Option<T>` (or `Vec<T>`). This gives back a
"declared but not yet built" state — the same one SystemVerilog has as a
null handle — and Chapter 13's "nothing is ever half-built" claim must be
amended rather than defended.

**D7. Identity is derived, never stored.** No parent pointer: the parent
owns children as fields, so a back-pointer is a cycle requiring `Rc`/`Weak`.
No stored name or path field either — the current hand-typed
`Logger::new("env.loga")` strings are unverified and silently lie when a
component moves. The walk accumulates the path and hands it down.

UVM needs `m_parent` for `get_full_name()` (we compute it), `get_parent()`
navigation (we reject it), and child registration (ours is structural). It
buys nothing we cannot get otherwise.

**D8. One context type per phase** — `BuildCtx`, `ConnectCtx`, `RunCtx`.
Each phase's legal operations are encoded in its type: `build_child` does
not exist on `RunCtx`, so adding a component during run *fails to compile*.
UVM catches the analogue at run time ("Attempt to connect … at or after
end_of_elaboration. Ignoring.").

**D9. The context is cloned per node**, carrying the accumulated path:

```rust
fn child(&self, name: &str) -> BuildCtx<'a> {
    BuildCtx { path: format!("{}.{}", self.path, name), rt: self.rt }
}
```

Services therefore sit behind a *shared* reference, not `&mut` — which also
means `ctx` need not be `&mut`, removing a class of borrow conflicts.

**D10. `ctx` carries identity; the store is ambient.** pyuvm's signature
already encodes the split: `ConfigDB().get(self, "", "MSG")` — ambient store,
identity passed in. The half rustdv lacks is the identity.

## 3. Configuration

**D11. `ConfigDb` is an ambient (global) resource.** Forced, not stylistic:
components read configuration at any time → therefore from code outliving
any phase → spawned tasks require `'static`, so no borrowed context → an
owned handle threaded everywhere is the plumbing tax again. A `thread_local!`
is safe because the executor is documented `!Send`, "it never leaves the sim
thread." rustdv already has an ambient service and does not admit it:
`log::info(...)` is a free function reaching a global sink.

**D12. `get()` takes a context and a concrete path; `set()` takes a glob**,
both relative to the caller's position. pyuvm enforces this — wildcards are
legal only when storing.

**D13. Three-tier resolution**, in order:

1. most specific matching path wins;
2. then highest precedence — `default_precedence - depth` during build, so
   the shallowest setter wins regardless of write order; run-time writes use
   `default_precedence` and outrank all build-time writes;
3. then most recent write.

Tier 2 is load-bearing and cannot be dropped: build is top-down, so an
ancestor writes *earlier* than a descendant, and "last write wins" alone
would invert the expected result.

*Divergence to state in the book:* SystemVerilog does not sort by
specificity at all — `get()` gathers every regex match and takes the highest
precedence. Specificity-first is pyuvm's rule. We keep pyuvm's.

**D14. Failure is loud.** SV's `get()` collapses four distinct failures —
never set, path mismatch, field typo, *type mismatch* — into `return 0`,
leaves the `inout` value untouched, and returns a discardable `bit`. That is
the silent zero. Ours returns `Result` with a distinguishing error, marked
`#[must_use]`, returning an **owned value** so no borrow into the store is
held across a call into user code.

SV's config DB is type-*parameterized*, not type-*safe*: `T` filters a
runtime lookup and nothing correlates a `set` with a `get`. Rust's
contribution here is error clarity, not typing.

**D15. Typed keys are an ergonomic option, not the mechanism.** File-driven
testbenches have open-ended knobs with no compile-time Rust type, and
`TypeId` cannot distinguish two `u32` knobs on one component — which is why
UVM has a field name. String keys stay first-class.

**D16. The runner clears the store between tests.** A singleton persists
across tests in one process; pyuvm has `ConfigDB().clear()` for exactly this.

## 4. TLM

**D17. Ports live in components; exports live on FIFOs; FIFOs are
components** instantiated beside the components they connect, as children of
the parent. A connection is always *port → export*, never component →
component. Two components communicate by connecting to the same FIFO and
neither learns the other exists.

**D18. The capability zoo becomes traits; the names become type aliases.**
~9 primitive traits (put/get/peek/transport × blocking/nonblocking, plus
analysis); composites are one-line supertraits with blanket impls; port
names are `type` aliases over a single `Port<I>`. Nothing multiplies except
names.

**D19. Full name parity.** Ship every UVM port name. API completeness and
curriculum are separate decisions — the book teaches the common subset and
notes the rest exist. An engineer who greps for `get_peek_port` and finds
nothing concludes the framework is thin.

**D20. `_imp` classes are not ported.** They exist only because
SystemVerilog lacks multiple inheritance; a Rust component simply
`impl Put<T> for Scoreboard`.

**D21. `m_if_mask` is not ported.** UVM checks interface *subsetting* at run
time with a bitmask because SV cannot express "provides at least this
capability set." Supertrait bounds do it at compile time.

**D22. Cardinality is checked at elaboration**, reporting every unconnected
port at once — not lazily at first use (pyuvm) . This is `resolve_bindings`'s
min/max check, and it cannot be a compile-time check: late binding and static
completeness are mutually exclusive.

**D23. FIFOs keep their built-in `put_ap` / `get_ap` analysis taps.**

**D24. FIFOs expose separately-named export objects** so each has a path and
appears in the hierarchy; only the blocking/nonblocking/peek combinatorics
collapse into traits.

## 5. Interior mutability

**D25. Exactly two places in the framework need it:** the TLM FIFO's queue
and the `ConfigDb`. `Rc`/`RefCell`, not `Arc`/`Mutex`, because the executor
is single-threaded. Chapter 13's "you almost never need this" survives for
user code and needs two stated exceptions.

---

## 6. Chapter 23 specifics

**D26. No factory in Chapter 23.** The book does not use it there; it
arrives in Chapter 29.

**D27. `#[rustdv::test]` annotates a struct or type alias**, registering the
component by name so the runner can `run_test("random_test")` — UVM's
`run_test()` restored. It no longer annotates a free function.

**D28. Shared behavior is a generic base, not inheritance-by-composition.**
`AluTest<T: Tester>` is written once; `RandomTest` and `MaxTest` are type
aliases. "Extends, overriding one thing" becomes "a type alias for a generic
base." The varying type is a real field, so no `PhantomData` and no marker
object — holding an object to carry behavior is a SystemVerilog reflex.

## 7. Repository conventions

**D29. Chapter crate roots are named after the crate**, not `lib.rs`
(`path = "src/ch23_uvm_test_testbench_3_0.rs"`). Twenty-five identical
`lib.rs` files are unsearchable and unreadable in an editor tab bar; Rust
moved off `mod.rs` in 2018 for the same reason.

**D30. Do not split Part II chapters by figure.** Part I figures are
standalone programs — one file each is right. A Part II chapter is a single
testbench built from interdependent figures.

**D31. Renames precede transcript regeneration.** Log lines embed
`file:line`, so every rename touches every transcript that shows a log
message.

---

**D32. Rust naming convention wins: `ConfigDb`, not `ConfigDB`.** Matches
`HashMap`, `TcpStream`, `Utf8Error`.

**D33. The BFM is not a component** — it is the analogue of a SystemVerilog
virtual interface, not a hierarchy participant. It stays a plain field,
shared by `Rc`, with no path and no phases.

**D34. Phase traversal follows pyuvm, not SV UVM.** So: `build` top-down,
`connect` bottom-up, `run` bottom-up, and `end_of_elaboration`,
`start_of_simulation`, `extract`, `check`, `report`, `final` all top-down.
SV UVM makes the middle five bottom-up. The book must state the divergence
plainly rather than let a reader assume 1800.2 behavior.

**D35. This document does not become the architecture documentation.** It is
a changing decision log with no teaching structure. Architecture
documentation is a separate document, written once the design settles.

## 9. Emulation

**D36. Emulation is a Day-1 target, not a later port.** In co-emulation the
DUT runs in hardware at MHz while the untimed side runs UVM in a simulator —
so the *software side is very often the bottleneck*. A compiled,
monomorphized, GC-free testbench attacks exactly that bottleneck, and an
order of magnitude on the untimed side changes the economics of owning an
emulator. This is plausibly rustdv's largest opportunity.

**D37. The BFM is the portability boundary.** Above it — sequences,
scoreboards, coverage, configuration, factory — is untimed and portable.
Below it is either software pin-wiggling (simulation) or a synthesizable
transactor (emulation). One testbench, two deployments.

**D38. Two audiences, two front doors, both first-class.** rustdv must serve
the *timed* world of FPGA engineers (signals, clocks, pins — cocotb-shaped,
no components required) and the *untimed* world of emulation engineers
(transactions only). **The component layer is optional.** A complete, useful
testbench must be writable with a DUT handle and signals and no `Component`
at all. Part II stays a legitimate destination, not a stepping stone.

**D39. Timed/untimed separation is convention, not compiler-enforced.**
Emulation engineers can be trusted to follow it. *(Rejected: giving untimed
components a restricted context so they structurally cannot reach a signal.
It taxes the FPGA majority to serve the emulation minority.)* Consequence:
DUT access stays universally available on the context — `ctx.dut()` is fine.

**D40. Clock generation is a convenience, not infrastructure.** `Clock`
stays in rustdv for those who want it, but it is not the recommended path
and rustdv never generates a clock implicitly. **BFMs wait on edges; they
never drive them** — which is what makes a BFM port to an emulator unchanged.

**D41. Clock generation belongs in `run`, not `build`.** It is an activity,
not structure, and a task started during `build` runs before any objection
exists. cocotb does the same: `start_soon(Clock(...).start())` in the test
body.

## 11. Findings from the source books

Both books' examples are now in `/reference` — `uvmprimer-master` (SV UVM)
and `Python4RTLVerification-master` (cocotb/pyuvm). The Python book's chapter
numbers map directly: its `27_uvm_test_testbench_3.0` is rustdv's ch23.

**D42. The RTL supplies the clock; rustdv generates none.** The Python
book's `tinyalu.sv` self-clocks — `bit clk; initial clk = 0; always #5 clk =
~clk;` — with `clk` an internal signal, not a port, and the BFM only ever
does `await FallingEdge(dut.clk)`. The SV Primer declares and drives `clk`
inside the `tinyalu_bfm` interface. The single software `Clock()` in the
whole Python repo is in the chapter that *teaches* cocotb's Clock.

rustdv's `sim-common/hdl/tinyalu.sv` declares `input clk` and generates
nothing, which is the sole reason every sim example carries a software clock
line. **Action: make rustdv's `tinyalu.sv` self-clocking and delete the
`Clock::new(...)` line from every sim chapter.** `Clock` stays in the
framework and is taught once, as a cocotb feature.

**D43. At 3.0 the test is the only component.** In the source, `BaseTest`
creates the BFM and scoreboard as *locals inside `run_phase`*; the tester is
a plain object; `build_phase` does exactly one thing — choose the tester.
There are no children until ch24 and no env until ch25. rustdv's ch23 must
not introduce a component tree three chapters early.

**D44. Testers are values, not components.** rustdv already models this
correctly: `Tester` is a trait with `get_operands()` required and
`execute()` supplied as a **default method** — Rust's native form of the
template-method pattern the books express with an abstract base class.
Nothing about a tester needs building, a path, or a phase. *(This dissolved
the former Q4: nothing constructs a tester generically, so `Tester` needs no
constructor. It also removes the last need for `dyn Tester`, so `execute`
stays static-dispatch with no `BoxFuture`.)*

**D45. Share infrastructure; inline pedagogy. Each chapter example is
self-contained.** Every Python chapter imports only `TinyAluBfm`, `Ops`,
`alu_prediction` (and sometimes `logger`) and **defines everything else in
the chapter file**, explicitly marked `# Copied from testbench 2.0`.

The reason is not laziness about DRY — the classes *evolve*. `BaseTester()`
is a plain class at 3.0 and `BaseTester(uvm_component)` at 4.0. Re-showing
them is how the reader sees the change, and that change is the book's arc.
Factoring them into a shared crate does not merely hide them; it makes the
thing the book is teaching invisible.

rustdv currently promotes them into `tinyalu_utils::{tb2, tb4, tb6, tb7,
env7}`, so a chapter file shows only imports. **Action: dissolve those
modules back into their chapter files.** `tinyalu_utils` keeps the BFM,
`Ops`, `CmdTuple`, and `alu_prediction` — infrastructure only. Applied to
ch23; the rest follow as each chapter is converted.

**Observation, not yet a decision: the BFM is ambient in both books.**
Python: `class TinyAluBfm(metaclass=pyuvm.Singleton)` — the test, tester and
scoreboard each call `TinyAluBfm()` and get the same object. SystemVerilog:
`uvm_config_db#(virtual tinyalu_bfm)::set(null, "*", "bfm", bfm)` in
`top.sv`. Neither passes it down. rustdv threads `Rc<TinyAluBfm>` through
constructors — the same plumbing-versus-ambient tension we resolved for the
ConfigDb, appearing a second time. See Q11.

**Observation: the ConfigDb is load-bearing in the *first* UVM testbench.**
That `set(null, "*", "bfm", bfm)` is in Primer chapter 11 — the hello-world
UVM test. In SystemVerilog you cannot write even the simplest UVM testbench
without the config DB, because it is how the virtual interface reaches the
components. See Q12.

## 10. Open questions

| # | Question |
|---|---|
| Q4 | **How does a generically-built tester get constructed?** `AluTest<T: Tester>` writes `T::something()`, so `Tester` must promise a constructor. Candidates: `fn new(rng: Rng) -> Self` (every tester takes an RNG; `MaxTester` ignores it); `Default` plus an RNG passed to `execute`; or `fn new(ctx: &BuildCtx) -> Self` (the tester takes what it needs). Leaning toward the third. |
| ~~Q8~~ | **Resolved — see D42.** |
| Q9 | **Does the single-threaded (`!Send`) executor survive D36?** It buys cheap `Rc`/`RefCell` (D25) and is right for a simulator. If the software side is the bottleneck in co-emulation, multiple cores may eventually matter. |
| Q10 | **`rustdv-gpi` binds VPI directly.** A transaction-level backend is not a variant of that — it is a different shape. What does the bottom layer look like when there may be no signal-level interface at all? |
| Q11 | **Should the BFM be ambient?** Both source books make it so — pyuvm by singleton, SV by `config_db` wildcard. rustdv threads `Rc<TinyAluBfm>` through constructors instead. Making it ambient would remove BFM plumbing from every example. |
| Q12 | **Does the ConfigDb need to arrive earlier than ch27?** In SV it is how the virtual interface reaches components, and it appears in the first UVM testbench. rustdv's answer to "how does the BFM reach a component" is currently constructor arguments, which is the question Q11 asks. |
